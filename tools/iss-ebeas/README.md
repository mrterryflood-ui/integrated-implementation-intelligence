# ISS-EBEAS v1.1 enforcement package

This portable Node package implements the versioned ISS requirements contract. It
uses locked AJV dependencies without changing an application's dependency graph.
`iron_gate.py` is a byte-for-byte copy of the canonical IRON-ENG-001 receipt validator;
its SHA-256 is retained in `origin.json`. The existing IRON checks are not replaced.

## Run

From the repository root:

```sh
npm ci --prefix tools/iss-ebeas --ignore-scripts
node --test tools/iss-ebeas/gate.test.mjs
node tools/iss-ebeas/gate.mjs --stage build
node tools/iss-ebeas/gate.mjs --stage evidence
node tools/iss-ebeas/gate.mjs --stage release
```

The TS entrypoint `scripts/iss-audit-gate.ts` delegates to the same implementation
for repositories that already have a locked `tsx` runner. Do not install an
unversioned runner through `npx` during a release. The default invocation is the
strict **release** stage; unknown options fail.

| Stage | What runs | Honest successful result |
| --- | --- | --- |
| `build` | Strict manifest/risk target validation, actual source-root enumeration, scoped heuristic findings, checklist/test-path configuration, active-runtime artifact configuration | Configuration checked; release `NOT_EVALUATED` |
| `evidence` | Build checks plus exact source revision, signed-manifest preparation inputs, executed-check metadata and artifact digests, actual-user attempt metadata, measured budgets, SBOM, security findings, applicability, authority, existing IRON receipt | Evidence consistency checked; `PROVENANCE_PENDING` |
| `release` | All above plus actual `gh attestation verify` over the evidence manifest with pinned repository, workflow, source revision and GitHub OIDC issuer | `EVIDENCE_CHECKS_PASSED`; deployment, store approval and user outcome remain separate |

Each invocation writes `audit/attestation.json` when that fixed output path is
safe and writable. The receipt's `sha256Attestation` is a canonical-JSON integrity
digest; `signature: UNSIGNED_LOCAL_RECEIPT` is explicit. Malformed/missing manifest
or schema inputs produce a failure receipt. Unsafe output links are never followed;
the process exits nonzero and reports the failure instead.

The source scan records only paths and finding codes, never matched secret values.
It scans the declared roots, not the entire dependency/history graph. A component
name cannot excuse an OS permission call. Heuristic findings require independent
disposition and executed test evidence before release; no pattern matches is not
proof of secret absence, motion quality, permission sequencing or accessibility.

## Evidence transport contract

Release evidence is generated by actual test/build/review owners, retained as a
CI artifact, and imported into the `audit/` directory by the repository's bounded
release-evidence importer. It is not committed to source to solve a self-referential
commit hash. Never place real patient/customer data, tokens, session state, private
keys or participant identities in these artifacts. Human testers use nonidentifying
pseudonymous participant IDs and consented, protected original evidence.

Required files:

- `audit/ebeas-evidence.json`: manifest binding the full source revision, repository,
  scanned raw-byte `sourceDigest`, builder, timestamps, requirement results and
  original artifact hashes.
- `audit/iron-receipt.json`: the canonical IRON candidate receipt. Its SHA-256 is
  included as `ironReceiptSha256` in the EBEAS evidence manifest.
- Original build/test/browser/DB/review/security/applicability artifacts, all at
  bounded relative paths and referenced with SHA-256 digests.
- `audit/ebeas-evidence.sigstore.jsonl`: the actual Sigstore bundle produced after
  the `evidence` stage passes. A boolean or locally constructed checksum cannot
  replace this signature.

The evidence manifest has `version: "1.1.0"`, `revision`, `repository`, `createdAt`,
`builder`, and `checks` keyed by the checklist's requirement IDs. Every applicable
pre-promotion row must have `status: "PASSED"`, the exact `revision`, `executedAt`,
`method`, `runner`, a truthful `mode` (`static`, `synthetic`, `staging`, `live`, or
`manual`) and a nonempty `artifacts` array of `{path, sha256}`. Executed journey,
identity, persistence, isolation and audit checks also require nonzero
`executedCases`, zero `failedCases` and zero `skippedCases`; static claims cannot
discharge them. Extra declared requirements are retained. IRON/provenance/release
are evaluated by their own gates; deployment/live observations remain explicitly
post-promotion obligations.

Additional required evidence sections are documented by `validateEvidence()`:

- `measurements`: named device/network/workload, percentile 75, nonzero sample and
  INP sample counts, positive measured `fcpMs`, `inpMs`, `firstValueSeconds`, and
  `sustainedFps` meeting the declared targets.
- `userAcceptance`: actual human status; declared primary persona represented;
  bounded per-persona `attempts` with unique pseudonymous IDs, first-time status,
  completion, assistance count, first-value/full-outcome seconds, and a path to a
  hash-bound attempt artifact. At least three completed unassisted first-time
  attempts per persona must meet the declared clocks. Preserve unsuccessful
  attempts; a missing observed value is null for a failed attempt. The reported
  first-value p75 must match the retained attempts.
- `security`: zero open critical/high findings, an actual successful secret scan,
  and the parsed, hash-bound SBOM path. SBOM configuration is not a vulnerability
  scan and neither is this package's limited source heuristic.
- `cryptography`: actual trust boundary, key custody, recovery/revocation and,
  where required, independently reviewed CMVP certificate/module/version/
  operating-environment/approved-mode evidence. TLS is not payload E2EE.
- `approval`: distinct authorized approver, exact revision, authority reference
  and environment. This metadata does not authenticate a human; preserve original
  authority evidence and protected promotion controls.
- Empty `unresolvedFindings`, and independent `staticFindingDispositions` for
  every scoped heuristic finding with substantive rationale and test evidence.

The fixture helper creates deliberately synthetic and fabricated claims to test
rejection boundaries. **It must never produce product acceptance evidence.**

## Signing and remaining trust boundaries

The release workflow validates the original successful same-repository,
same-revision run and bounded artifact archive before checking its contents.
After evidence validation, the pinned GitHub attestation action signs the evidence
manifest; the verifier checks the resulting bundle. The manifest binds original
artifact hashes, including the built artifact retained in the IRON build receipt.
The hosting step must promote that verified artifact or provide an equivalent
exact-build binding; rebuilding arbitrary source afterward is not that proof.

`gh attestation verify` must be available in a trusted toolchain. The development
container's old CLI cannot execute it; negative tests demonstrate fail-closed
behavior, not successful cryptographic verification. GitHub's private-repository
attestation entitlement and protected environment configuration must be checked
in each repository. No upgrade, secret, signer entitlement or environment approval
is fabricated by this source package.

Signing authenticates origin and integrity; it does not prove that test reports,
participant records or legal claims are true. Independent reviewers inspect the
original producer receipts and instrument fit. Source-controlled workflow files
alone do not configure GitHub required checks, protected environment reviewers,
Railway automatic promotion, Replit publishing or App Store/Play Console authority.
Those integration gaps remain visible in the repository adoption record.

# Additive anonymous-static interpretation

`WEB_STATIC` uses `1.1.0-evidence.2-static` and a strict `platform.staticDelivery` declaration. It is only available for anonymous, read-only commercial/civic web delivery. Existing application manifests keep `1.1.0-evidence.1` and all of their existing authentication, encryption, framework, runtime and risk requirements.

This corrects scope representation, not release authority. Every original evidence requirement remains required. Static release additionally requires a hash-bound `STATIC_DELIVERY_APPLICABILITY_REVIEW` for the exact revision, source digest, entrypoints and declared boundary, with an independent reviewer and executed absence checks. Missing or unreviewed scope, failed tests, high vulnerabilities, absent real-user evidence, invalid IRON acceptance or unsigned provenance still fail. `node --test tools/iss-ebeas/gate.test.mjs` includes both ordinary-profile and static-profile regressions.
